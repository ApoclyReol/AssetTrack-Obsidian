# 13 月度结算体验设计

> 文档角色：开发与维护。这里规定用户体验和交互判断；不是用户操作手册。界面细节
> 还需与[设计系统](05-design-system.md)和[用户指南](02-user-guide.md)同步。

## 1. 体验目标

用户打开 Asset Track 时，首先应该知道三件事：

1. 这个月整理到哪一步了；
2. 还有哪些问题需要我判断；
3. 完成后我会得到什么结论。

界面应隐藏实现复杂度，但不能隐藏证据。用户不需要先理解数据库、规则层级或 revision
才能完成一次月度结算。

## 2. 月度结算状态模型

这是后续工作台的目标状态模型，当前页面可以逐步向它靠拢：

| 状态 | 用户看到的意思 | 主要行动 |
| --- | --- | --- |
| 未开始 | 本月还没有整理 | 导入账单 |
| 已导入 | 已经有数据，但还未完成检查 | 查看覆盖和异常 |
| 待整理 | 有分类、商品或规则问题 | 处理冲突和未分类 |
| 待补充资产 | 流水已有，月末资产信息不完整 | 更新现金、理财、借款区块和固定资产 |
| 待对账 | 资产与流水还没有闭合 | 查看差额并排查异常 |
| 已完成 | 本月事实已经整理并验证 | 查看分析和长期变化 |

每个状态都需要定义进入条件、完成条件、阻断问题、可忽略警告和下一步按钮。状态文案
应该使用用户语言，不直接显示内部状态名。

## 3. 系统与用户的分工

| 系统负责 | 用户负责 |
| --- | --- |
| 记住常用字段映射 | 确认本次账单来源和覆盖范围 |
| 统一不同平台的字段语义 | 判断收支映射是否符合自己的理解 |
| 应用稳定的分类规则 | 处理冲突、缺口和异常 |
| 汇总金额、分类、借款和资产变化 | 补充月末资产状态 |
| 提示对账差额和影响范围 | 确认批量修改和最终结算 |

默认原则是“自动处理重复工作，用户处理例外”。如果系统无法确定，就应该清楚地说
“需要你确认”，而不是悄悄选择一个结果。

## 4. 渐进式信息展示

### 第一层：首页和月度顶部

只显示：本月状态、已导入范围、待处理问题、对账结果、核心资产和消费变化。

### 第二层：问题处理区

用户点击问题后再看到：未分类、商品冲突、规则冲突、数据缺口和异常金额。

### 第三层：证据详情

用户继续点击后查看具体流水、分类分布、规则解释、计算依据和批量修改影响范围。

技术诊断、schema、revision 和运行时信息只在开发维护文档或明确的诊断入口出现，不
进入普通用户的主阅读路径。

## 5. 异常驱动

用户不需要逐笔审阅所有流水。系统应优先呈现：

- 未分类、空商品和明显无效记录；
- 日期或金额异常；
- 账单范围重叠或可能重复；
- 商品分类冲突、规则冲突和部分覆盖；
- 资产倒推差额；
- 与历史相比显著异常的来源、数量或金额。

异常卡片必须说明“为什么出现、影响什么、下一步做什么”。只显示一个红色数字而不
提供解释，不算完成设计。

## 6. 高影响操作必须可控

分类迁移、商品统一、历史回溯、恢复和其他批量修改遵循：

```text
查看影响范围
→ 生成预览
→ 用户确认
→ 原子写入
→ 显示结果
```

取消确认不能改变事实；失败时保留当前状态并告诉用户如何重试。自动建议可以减少
选择成本，但不能静默覆盖历史。

## 7. 用户文案模板

每个主要操作按四句话组织：

1. **你需要做什么**：一个明确动作；
2. **系统会做什么**：一句解释，不讲实现；
3. **完成后会看到什么**：结果或下一步；
4. **出现问题怎么办**：可执行的恢复方式。

导入账单的最短路径应保持为：

```text
选择账单
→ 确认字段
→ 查看接受、忽略和异常记录
→ 应用到本月
→ 保存月份
```

复杂字段契约、错误码和事务边界放入维护文档，不在主操作说明中展开。

## 8. 维护验收清单

新增或修改一个页面时，维护者应检查：

- 用户是否能看出当前结算阶段和下一步？
- 主页面是否优先显示需要判断的问题，而不是技术状态？
- 自动处理和用户确认的边界是否清楚？
- 批量修改是否先展示影响范围并可取消？
- 空、错、加载和完成状态是否都有用户语言？
- 用户是否能从结论回到具体流水？
- 窄窗口和中英文文案是否仍然可读？

## 9. 与现有界面的关系

固定资产摘要的响应式表格、规则冲突的预览确认、商品回溯和分类迁移已经体现了部分
原则。后续优化应优先把这些已有能力组织成清晰流程，不要在没有状态和下一步说明的
情况下继续增加独立卡片或复杂筛选器。
