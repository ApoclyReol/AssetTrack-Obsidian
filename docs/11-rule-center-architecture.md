# 11 规则中心与容错导入架构补充

> 文档角色：开发与维护。本文说明规则中心和导入接口边界；用户只需按
> [用户指南](02-user-guide.md)处理分类和异常。

本文补充 v2.1.0 当前架构中与导入容错、月流水警告、通用规则、汇总合并、批量操作和配置中心有关的接口边界。
它以 schema 13、月份 `saved` 状态和 SQLite 写入事务为事实边界。理财流水的 `account_key`
只用于加仓和提现，交易对手仍是流水统计字段，不参与账户关系或规则范围扩展。

## 导入契约

`src/domain/csv.ts` 负责 CSV/XLSX/XLS 的源文件解析和预览，不写数据库。
`CsvInspection.empty_values` 标记每个表头是否出现空单元格；状态列的空字符串以
`included_statuses: string[]` 中的 `""` 表示。缺少日期列使用 `__month_start__`，
空日期单元格也规范化为当前月份 1 日，并在 `CsvImportStats.defaulted` 中计数。非空日期按行独立解析，允许同一文件混用四位/两位年份、中文年月日、紧凑日期、Excel 序列日期和带时间值。

预览过滤独立统计跨月、状态过滤、忽略类型和无效行。无法解析的非空日期、空/非数字
金额和未映射的收支值进入无效统计；空商品和零金额仍作为流水保留，分类匹配由
Service 在预览后使用当前分类定义完成。
CSV 确认只把接受行写入当前 React 草稿，不调用通用流水操作预览，也不在导入链路自动应用规则；
规则应用由流水区的独立操作入口触发，确认后再进入草稿并随流水保存。
导入映射在接受行成功进入草稿后才写入插件设置；设置写入失败只产生“流水已加入，但映射未保存”提醒，
不得撤回草稿或把该设置失败伪装成导入失败。

## 月流水质检与写入

`validateTransactions` 返回带 `severity` 和 `blocking` 的结构化问题。无法解析日期、
金额或收支类型是错误；空商品、零金额、缺少/不匹配分类是警告。`MonthEditor` 只在
存在错误时停止保存，Repository 在同一月份事务中再次校验并只拒绝错误。写入后和
重新打开月份时重新运行质检，因此警告不会丢失；“暂存”仍是现有 `saved` 状态。

异常输入不会被写成可伪装的有效事实：错误行不会提交，事务失败会回滚账户、流水和
固定资产的同次修改。警告行的空分类写入空值，零金额写入 `0`。

## 配置中心一期

规则页首次进入使用轻量的 `ruleWorkspaceShell()`，再按当前页面需要加载
`ruleWorkspaceAnalytics()`；规则候选由当前配置端口按需读取，不再保留旧的
`ruleWorkspace()`、`ruleInsights()` 或 `saveRuleWorkspace()` 公共接口。
数据健康直接使用 `productHistoryIndex({ issue_filter: 'conflict' })` 加载近 5 年商品-分类冲突表，并返回实际
读取范围；商品总览使用 `productOverview()` 默认加载最近 1 年，起止日期由用户选择，筛选变化后自动刷新。具体商品详情通过浮动回溯窗口加载，分类迁移 Modal
通过带 `category_key` 的 `productHistory()` 加载指定分类下的全部商品。历史查询只连接
`month_status.status='saved'` 的月份；空商品按独立商品键展示，不会因为商品为空而从统计中消失。

规则解析统一由 `src/domain/rules.ts` 提供，按收支类型和规范化交易对手/商品建立三种作用域唯一匹配键。
相同键命中多个不同分类时，兼容诊断会返回冲突并让 `applyRulesWithIssues()` 保留原分类；
正常保存路径会阻止同一键重复写入；组合、商品、交易对手按固定优先级解析一次，重写结果不触发第二轮。
重写后再次命中时，只检查重写结果的最高优先级规则：同级无冲突且目标分类与源分类一致的规范化链允许保存，
更低优先级的覆盖规则不构成链冲突；最高优先级目标指向不同分类时仍阻止保存。
月流水和历史详情使用同一个解析结果，因此规则解释和规则 ID 不会因页面不同而产生分歧。

交易对方既是流水/历史字段，也是规则条件；规则页面维护收支类型、匹配作用域、交易对手、商品、可选重写字段和分类。

`productHistory(query)` 返回稳定的数据库流水 ID、月份、日期、交易对方、商品、原分类、
分类启用状态、金额和规则解释。商品统计按“收支类型 + 规范化商品”聚合，商品-分类冲突按
商品级审计。多数分类只作为建议，不自动改写历史。

规则审计状态与实际覆盖范围由后端独立计算。数据健康直接显示商品-分类冲突；旧规则硬冲突和跨分类重写链只保留为兼容诊断与历史回溯保护，
正常跨作用域覆盖只在流水解释和汇总覆盖状态中显示，不误报为冲突。规则建议只根据未覆盖且分类稳定的流水生成。

分类回溯通过 `previewCategoryBackfill()` 和 `applyCategoryBackfill()` 完成。请求携带
`transaction_ids`、`target_category_key` 和每个受影响月份的
`expected_month_revisions`；预览展示旧分类分布、流水数、月份数和 revision。写入在
`DatabaseManager.write()` 的单个 SQLite 事务中完成，只更新 `category_key` 与 `category`，
每个月份 revision 增加一次，任何流水校验、分类类型校验或 revision 冲突都会整批回滚。

商品统一通过 `previewProductRename()` 和 `applyProductRename()` 完成。窗口默认使用当前
商品的收支类型和出现次数最多的分类查询；未分类商品默认选择未分类。用户可切换分类并
按商品搜索自动刷新，选择多个商品组。请求携带 `transaction_ids`、`target_product` 和每月
`expected_month_revisions`；写入只更新 `transactions.product`，不自动同步规则。统一商品
名称后刷新商品-分类冲突统计。

分类定义、属性/标签定义和匹配规则分别通过 `saveCategories()`、`saveTaxonomy()` 与 `saveRules()` 保存，并分别检查 revision；分类属性虽然在同一配置页展示，但仍使用各自的保存边界；匹配规则表的流水数和最近月份只显示近 1 年读取窗口内的历史数据，
商品总览负责用户选择范围内的统计，默认近 1 年。分类删除失败和确认都使用原生 Modal。旧规则冲突由现有规则和已保存流水派生为
`RuleConflictGroup`，仅用于兼容诊断和阻止可能覆盖历史语义的回溯；当前界面没有独立规则冲突面板。回溯成功后
发布现有数据变更事件：无草稿的月份窗口重新读取数据库，有草稿的窗口保留草稿并提示外部 revision 已变化，
旧草稿最终仍由 revision 校验保护。

## 规则洞察与能力端口

`ruleWorkspaceAnalytics(minOccurrences = 2)` 查询最近 1 年已保存月份中的 `transactions`，
不读取 React 草稿，并返回实际读取范围。配置 UI 通过 `ConfigurationEditorPort` 访问它，并返回规则 revision、
推荐分类规则和历史商品统计：

- 推荐按规范化的收支类型和商品聚合；历史统计按收支类型和商品聚合，并给出变体、交易对方、
  分类次数、置信度、月份数和最近月份；
- 历史统计给出总/平均/最近金额、最近日期、分类冲突、分类启用状态和匹配规则状态；
- 完全相同的规范化规则标为重复，通配字段与具体字段重叠且分类不同标为冲突；同一历史
  商品出现多个分类也标为历史冲突；
- 创建推荐规则使用当前规则 revision，成功后只新增 `auto_rules`，不回写历史账单。

规则界面消费同一规则解析结果，分类定义、已保存匹配规则和数据健康表各自维护排序与内部滚动容器。
商品详情、商品统一、分类迁移和规则创建使用浮动原生 Modal；历史回溯和商品统一仍必须生成 revision 预览
后才能确认写入，规则创建与规则表保存直接保存当前规则草稿；商品总览提供规则创建入口，不提供“打开最近月份”导航入口。
流水批量操作统一使用 `TransactionOperationPreviewRequest`，批量编辑在同一个编辑窗口中显示简要前后对比，确认后进入草稿，
保存时由 Repository 在同一月份事务中重新校验目标和 revision，并写入 `operation_logs`。AI 批次预览也写入本地审计元数据，不产生专用财务表。

标签批量操作使用 `bulk-add-tag`、`bulk-remove-tag` 和 `bulk-replace-tags` 三种 operation kind。
标签关联落在 `transaction_tags`，不会进入导入或规则自动应用；配置页的属性组、选项和标签定义
使用独立 revision，引用中的定义停用优先，未引用定义删除前先创建保护快照。

## 金额规则与区间（v2.1.0）

### 条件模型与边界

金额是商品/交易对手文字条件的附加限制；不提供仅金额规则。支持支出、收入、代付，理财流水仍不参与。
UI 提供七种方式，持久化沿用 `match_amount_minor`，并增加可空的 `match_amount_min_minor`、
`match_amount_max_minor` 和两个布尔字段 `match_amount_min_exclusive`、`match_amount_max_exclusive`。
精确值与范围互斥；缺少端点时不能声明该端点为开区间。

所有端点先校验为非负安全整数分。`ruleAmountBounds()` 将条件映射为包含两端的整数分区间：

| UI 条件 | 存储 | 规范范围（分） |
| --- | --- | --- |
| 不限金额 | 精确值、上下限均为 NULL | `[0, +∞)` |
| 等于 19.90 | 精确值 1990 | `[1990, 1990]` |
| 低于 2.00 / 不超过 2.00 | 上限 200，排除 / 包含 | `[0, 199]` / `[0, 200]` |
| 高于 100.00 / 至少 100.00 | 下限 10000，排除 / 包含 | `[10001, +∞)` / `[10000, +∞)` |
| 区间 2.00 至 50.00 | 下限 200、上限 5000，端点分别选择 | 闭区间 `[200, 5000]`，开端点相应增减一分 |

相同端点均包含时等价于精确金额；有任一端点排除则为空，拒绝保存。低于 0、反向区间、
分数分、NaN、Infinity、越界整数和大于安全最大值的开下限都无效。金额使用既有流水的两位小数归一化口径，
不使用浮点 epsilon、模糊金额或自动容差。未配置的区间空档保持未命中。

### 优先级、去重与重叠

固定顺序为精确金额 > 区间 > 不限金额，每档再按组合 > 商品 > 交易对手，共九档。
精确金额例外可以位于区间内；区间大小不会影响优先级。普通应用始终只解析一轮。

规范条件键包含收支类型、作用域、规范化文字条件和规范范围。生成列 `match_amount_min_key`、
`match_amount_max_key` 存储包含端点的规范值，无上限使用 -1；与文字字段组成六列唯一索引。
`<2.00` 与 `≤1.99`、`[2.00,2.00]` 与 `=2.00` 被视为同一条件。

同一文字条件中的两个区间只要有交集就拒绝保存，无论目标分类是否相同。
服务在事务写入前返回 `amount-overlap`、冲突行号和交集上下限，影响预览使用相同校验。
不同文字作用域沿用固定优先级；精确例外和不限金额兜底不算区间重叠。
匹配器面对外部损坏的同档冲突仍拒绝选择，避免随列表顺序决定结果。

重写链检测按所有相关端点划分金额区段，并检查交集中的实际可达目标，避免仅抽查区间下限遗漏
中间价格的跨分类链。规则统计计入实际满足文字与金额条件的流水；影响预览另外报告被更高优先级覆盖的数量。

### 界面与各读取入口

新建规则窗口直接显示方式、金额/上下限及“包含下限/上限”。已保存规则表使用紧凑条件按钮，
点击后在 Obsidian 原生 Modal 中编辑；应用到规则草稿后仍需保存规则。非法输入保留原文以便纠正，
同时阻止确认；清空必填金额不会变成不限金额，需明确切换方式。
搜索、金额排序、历史统计、规则应用、影响预览和重写链共享同一金额模型。合并只按整数分累加当前金额。

### 实际流水合并

v2.1.0 合并与规则匹配解耦，不再反查重写名称，不要求已匹配、唯一规则或相同金额。
入口只保留汇总行的“合并成一条”，当前可见组至少两笔即可预览；底层继续拒绝跨月份、跨类型、
理财流水、错误金额、重复标识和不属于同一商品/交易对手汇总的来源。
`normalizeTransactionLabel()` 是 UI 分组和领域校验共享的组身份，允许既有的 NFKC/空白/标点变体。
结果金额是普通累计金额，后续显式应用规则重新按该金额判断，累计结果仍可再次合并。

`MonthEditorPort.previewTransactionMerge()` 接收当前草稿、可见组成员 key、分组维度、月份 revision 和标签开关，不携带规则 revision；
领域预览以当前分类与完整标签组合分区，产生新 client_id、各组 before/after、被清空的次要名称字段和草稿检查点。
日期为当月 1 日、金额按分累加；分类取当前值，汇总字段保留，另一名称完全相同则保留，不同则留空。
确认只替换 React 草稿；`merge-transactions` 在月份保存事务中独立校验多笔删除/一笔新增，不能套用逐行更新协议。
手工修改只清理普通过期预览，保留合并审计；保存记录确认时结果、最终结果及新数据库 ID，不提供拆分恢复。

### 迁移与备份

正式升级为 schema 12→13，一次加入精确金额、范围、规范键和 `rewrite_empty_mode`。
旧规则 ID、分类和流水保留，原规则不限金额，重写留空默认 `preserve`。首次进入插件只读检测，
原生 Modal 展示目录和影响，用户确认后先创建 `before-schema13-*.db` 保护备份，再单事务升级。
取消不写入，页面提供重试；设置页仍可手动载入及处理更早版本的属性保留/清除。

为兼容已使用本地开发版的数据，识别结构而不只比较编号：旧开发 schema 13 仅有精确金额，
14 有范围但无重写策略，15 包含完整规则字段；它们均在保护备份后补齐或规范为正式 schema 13。
完整 schema 13 不重复升级，部分损坏的结构和其他未来版本拒绝打开，不能当作旧开发版修复。
备份验证同样兼容这些结构，当前 schema 13 与旧开发同号结构通过字段区分。

完整备份格式 12 包含所有金额列、生成键和重写留空行为，兼容格式 8/9/10/11。CSV 摘要通过 `table_xinfo` 识别生成整数列，
保证 SQLite 数值与 CSV 数字文本按同一数值类型校验。恢复仍先验证、创建保护快照再替换，不自动迁移正式 Vault。

## 重写与标签合并

`rewrite_empty_mode` 为 `preserve` 或 `clear`，旧规则默认 `preserve`。`rewriteRuleFields()` 统一服务普通规则应用与
批量规则预览：已填写重写值优先，空白重写按策略保留来源字段或清空，不把匹配条件当作隐式重写值。合并不执行重写。
规则表将两个重写列合为原生 Modal 按钮，三个设置一次应用到规则草稿，保存规则后才持久化。

`include_tagged` 默认 false，带标签来源保留；显式勾选后，按排序去重后的完整 `tag_keys` 组合分区。
分区键同时包含当前 `category_key` 和分类名称，未分类不会并入其他分类。每个分区至少两笔才生成结果，
不足两笔保留明细。每笔来源只属于一个分区，因此总金额、分类金额及逐标签金额保持一致。

预览返回 `selected_count`、`excluded_tagged_count`、`unchanged_count`，操作日志 selection 只包含被替换来源。
操作日志用 `merge_policy: summary` 标记当前协议，不携带规则归属。Repository 在保存事务中，
根据记录的标签选项和来源草稿重新分区校验，伪造选项、输出字段或组数将回滚整个保存。
纯合并不受规则版本变化影响；同批日志若先应用规则，该操作仍须通过规则 revision 校验。月份 revision 始终校验。
合并 Modal 使用统计摘要、范围选项、字段预览和明细折叠，底部确认说明与操作保持可见。

规则列表的搜索/分组/四类筛选位于一行，依据容器宽度换行；独立排序和重置控件移除，所有表头统一排序，含编号。
客户端草稿即时检测重复、金额区间交集、跨分类重写链，列出规则 ID 或新规则序号、文字/金额条件和分类，并标记行。
服务错误同样返回参与规则 ID 与草稿位置，不能仅使用一句泛化冲突描述。
