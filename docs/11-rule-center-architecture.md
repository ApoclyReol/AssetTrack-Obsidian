# 11 规则中心与容错导入架构补充

> 文档角色：开发与维护。本文说明规则中心和导入接口边界；用户只需按
> [用户指南](02-user-guide.md)处理分类和异常。

本文补充 v1.4.0 当前架构中与导入容错、月流水警告和规则中心有关的接口边界。它不改变
schema 9、月份 `saved` 状态或 SQLite 写入事务。

## 导入契约

`src/domain/csv.ts` 负责 CSV/XLSX/XLS 的源文件解析和预览，不写数据库。
`CsvInspection.empty_values` 标记每个表头是否出现空单元格；状态列的空字符串以
`included_statuses: string[]` 中的 `""` 表示。缺少日期列使用 `__month_start__`，
空日期单元格也规范化为当前月份 1 日，并在 `CsvImportStats.defaulted` 中计数。

预览过滤独立统计跨月、状态过滤、忽略类型和无效行。无法解析的非空日期、空/非数字
金额和未映射的收支值进入无效统计；空商品和零金额仍作为流水保留，分类匹配由
Service 在预览后使用当前分类定义完成。

## 月流水质检与写入

`validateTransactions` 返回带 `severity` 和 `blocking` 的结构化问题。无法解析日期、
金额或收支类型是错误；空商品、零金额、缺少/不匹配分类是警告。`MonthEditor` 只在
存在错误时停止保存，Repository 在同一月份事务中再次校验并只拒绝错误。写入后和
重新打开月份时重新运行质检，因此警告不会丢失；“暂存”仍是现有 `saved` 状态。

异常输入不会被写成可伪装的有效事实：错误行不会提交，事务失败会回滚账户、流水和
固定资产的同次修改。警告行的空分类写入空值，零金额写入 `0`。

## 规则工作台一期

规则页保留 `ruleWorkspace(minOccurrences?)`、`ruleInsights()` 和 `ruleCandidates()` 兼容接口，
界面首次进入使用轻量的 `ruleWorkspaceShell()`，再后台加载 `ruleWorkspaceAnalytics()`。
分类定义、已保存匹配规则和规则健康摘要在主页面显示；健康摘要点击后进入商品/分类冲突、规则冲突或无规则商品内容面板。
商品统计默认使用 `productHistoryIndex({ issue_filter: 'conflict' })` 加载，健康问题面板隐藏问题类型选择器但保留收支、
分类、商品搜索、年份和最少次数筛选，筛选变化后自动刷新，不再提供手动加载按钮。具体商品详情再通过浮动回溯窗口按商品加载，
不增加第二层历史筛选。分类迁移 Modal 直接调用
带 `category_key` 的 `productHistory()`，加载指定分类下的全部商品并提供商品选择。历史查询只连接
`month_status.status='saved'` 的月份；空商品按独立商品键展示，不会因为商品为空而从统计中消失。

规则解析统一由 `src/domain/rules.ts` 提供，优先级固定为：收支+交易对方+商品、
收支+商品、收支+交易对方。相同优先级命中多个不同分类时返回冲突解释，
`applyRulesWithIssues()` 保留原分类；精确规则与泛规则的重叠在规则审计中标记为覆盖冲突。
完全相同的规范化键和分类标记为重复。月流水和历史详情使用同一个解析结果，因此规则
解释、命中层级和规则 ID 不会因页面不同而产生分歧。

命中层级只属于后台解析语义，规则页面不向用户显示层级或处理方法；用户只维护交易对方、商品和分类。

`productHistory(query)` 返回稳定的数据库流水 ID、月份、日期、交易对方、商品、原分类、
分类启用状态、金额和规则解释。商品统计按“收支类型 + 规范化商品”聚合，分类冲突按
商品级审计；精确候选按“交易对方 + 商品”生成，只有跨多个交易对方且历史分类完全稳定
时才生成商品级候选。多数分类只作为建议，不自动改写历史。

规则审计状态与实际覆盖范围独立计算。每个商品组返回 `rule_coverage`、命中次数、未命中
次数和冲突次数；某一交易对方命中精确规则时，不会把其他交易对方的流水误标为全部覆盖。
“无规则”筛选和健康摘要同时包含完全未覆盖与部分覆盖商品。没有未解决规则冲突时，
`rule_suggestion` 只根据未覆盖流水生成：单一交易对方建议交易对方与商品组合，跨交易
对方且分类稳定时建议商品条件。

分类回溯通过 `previewCategoryBackfill()` 和 `applyCategoryBackfill()` 完成。请求携带
`transaction_ids`、`target_category_key` 和每个受影响月份的
`expected_month_revisions`；预览展示旧分类分布、流水数、月份数和 revision。写入在
`DatabaseManager.write()` 的单个 SQLite 事务中完成，只更新 `category_key` 与 `category`，
每个月份 revision 增加一次，任何流水校验、分类类型校验或 revision 冲突都会整批回滚。

商品统一通过 `previewProductRename()` 和 `applyProductRename()` 完成。窗口默认使用当前
商品的收支类型和出现次数最多的分类查询；未分类商品默认选择未分类。用户可切换分类并
按商品搜索自动刷新，选择全部分类时必须提供搜索条件，再按“分类 + 商品”或“商品”聚合
选择多个商品组。请求携带 `transaction_ids`、`target_product` 和每月
`expected_month_revisions`；写入只更新 `transactions.product`，不自动同步规则。统一商品
名称后保留冲突面板原筛选、刷新统计并重新计算规则状态，用户再单独处理规则冲突。

分类定义和匹配规则分别通过 `saveCategories()` 与 `saveRules()` 保存，并分别检查 revision；分类表只显示历史流水数，不显示商品冲突；商品冲突表只保留冲突处理所需字段，完整交易对方数、月份数和金额统计由分析页 `productOverview()` 提供。分类删除失败和确认都使用原生 Modal。规则冲突由现有规则和已保存流水
派生为 `RuleConflictGroup`，区分重复规则、同条件不同分类和条件重叠，显示影响流水和月份；用户只能编辑
或删除规则，不自动合并或按数据库顺序选择。规则冲突未解决时，商品分类迁移不允许生成预览。回溯成功后
发布现有数据变更事件：无草稿的月份窗口重新读取数据库，有草稿的窗口保留草稿并提示外部 revision 已变化，
旧草稿最终仍由 revision 校验保护。

## 兼容接口与规则洞察

`AssetTrackService.ruleInsights(minOccurrences = 2)` 由
`AssetTrackRepository.ruleInsights` 实现，查询全部已保存月份中的 `transactions`，
不读取 React 草稿。服务返回规则 revision、推荐分类规则和历史商品统计：

- 精确推荐按规范化的收支类型、交易对方和商品聚合；历史统计按收支类型和商品聚合，并给出
  变体、交易对方、分类次数、置信度、月份数和最近月份；
- 历史统计给出总/平均/最近金额、最近日期、分类冲突、分类启用状态和匹配规则状态；
- 完全相同的规范化规则标为重复，通配字段与具体字段重叠且分类不同标为冲突；同一历史
  商品出现多个分类也标为历史冲突；
- 创建推荐规则使用当前规则 revision，成功后只新增 `auto_rules`，不回写历史账单。

规则界面消费同一规则解析结果，分类定义、已保存匹配规则和健康问题面板各自维护排序与内部滚动容器。
商品详情、商品统一、分类迁移和规则创建使用浮动原生 Modal；历史回溯和商品统一都必须生成 revision 预览
后才能确认写入；推荐信息融合在无规则商品面板，不再单独显示宽表，也不提供“打开最近月份”导航入口。
