# 16 界面回归测试协议

> 文档角色：开发、测试和 debug 交接协议。本文规定每次源码或构建更新后，哪些流程必须在真实 Obsidian 界面中点击验证；不替代 Vitest、typecheck、lint、构建和数据库测试。

## 0. 使用原则

Asset Track 的 React 测试可以证明组件和状态转换，但不能证明 Obsidian 真的加载了最新
`main.js`、弹窗没有被宿主覆盖、CSS 在真实主题下没有破坏表格布局，也不能证明键盘焦点、
滚动、原生 Modal 和重载行为正常。因此，以下结果只有在“实际打开插件并完成点击”后才能记为
通过：

| 结果 | 含义 |
| --- | --- |
| `通过（日期/版本/测试人）` | 已在目标 Obsidian 窗口完成规定点击，并观察到预期结果 |
| `失败（issue）` | 可稳定复现，已记录环境、步骤和证据 |
| `阻塞（原因）` | 测试环境、数据夹、版本或权限阻止继续，不能当作通过 |
| `未测试` | 本轮没有实际点击，不得根据源码或自动化测试推断为通过 |

禁止使用以下替代说法：

- 只看到源码或单元测试通过，就声称界面已修复；
- 只打开页面，不点击入口、确认、取消和重载路径；
- 只在开发热加载页面测试，不验证最终 `build/` 三文件；
- 用真实 Vault、真实账单、真实数据库路径或私有截图作为交接证据；
- 将“插件没有崩溃”当作保存、迁移、回滚或数据语义通过。

## 1. 每次更新后的固定顺序

接手测试的对话按下面顺序执行；若某一步失败，先记录证据，再决定是否进入 debug，
不要跳过失败继续给出“整体通过”。

### 1.1 自动门禁

在仓库根目录执行：

```bash
npm run typecheck
npm run lint
npm test
npm run build
npm run release:check
git diff --check
bash scripts/smoke_test_plugin.sh build
```

如果修改了依赖、版本、通知文件或发行配置，再按项目要求补跑：

```bash
npm run notices:update
```

自动门禁通过后，确认 `build/` 根目录只有 `main.js`、`manifest.json` 和 `styles.css`。
不要直接编辑 `build/`，也不要使用旧构建产物。

### 1.2 安装产物一致性

将同一次构建生成的三个文件加载到隔离测试 Vault 的插件目录。测试前必须确认：

1. 插件目录中的三个文件来自本次 `build/`，不是旧缓存；
2. `manifest.json` 版本与根目录版本源一致；
3. Obsidian 已重新加载插件；
4. 如仍怀疑缓存，完全退出并重新启动 Obsidian，再执行一次代表性流程；
5. 记录 Obsidian 版本、插件版本、操作系统、主题、界面语言和窗口宽度。

可用哈希确认文件确实相同，但哈希不能代替界面点击：

```bash
shasum -a 256 build/main.js build/styles.css build/manifest.json
```

### 1.3 测试数据准备

优先使用隔离 Vault、合成数据库或测试 fixture。至少准备以下数据状态：

| Fixture | 用途 | 最小内容 |
| --- | --- | --- |
| `empty` | 首次启动和空状态 | 没有数据库，或刚创建的空数据库 |
| `basic-month` | 月度工作台和流水 | 一个已保存月份、出账/入账/理财各至少一行 |
| `taxonomy` | 分类、属性和标签 | 一个分类属性、两个标签，其中一条流水已关联标签 |
| `history-conflict` | 数据健康和历史迁移 | 一个商品跨月份出现不同分类或部分规则覆盖 |
| `migration-copy` | schema 迁移和取消 | 复制的 schema 9/10/11 合成数据库，不使用生产文件 |
| `import-fixtures` | 导入映射 | UTF-8、GB18030、CSV、XLSX/XLS 和异常行样本 |
| `large-synthetic` | 性能和滚动 | 由测试脚本生成的合成数据，不含真实账单 |

数据 fixture 的具体字段以当前 schema 和测试代码为准；协议不允许把真实数据库路径、
真实商品名、真实账单内容或 API 密钥写进测试记录。

## 2. 变更到点击场景的路由表

一次更新只需要执行“受影响场景”并保留固定冒烟；如果改动跨越多个边界，取所有场景的并集。

| 改动范围 | 必测场景 | 需要额外关注 |
| --- | --- | --- |
| `src/ui/TaxonomySelectionModal.ts`、`TransactionTables.tsx`、流水操作 Modal | `UI-TXN-01`～`UI-TXN-05` | 真实已有标签、标签草稿、取消、保存和重载 |
| `src/ui/configuration/`、`RulesEditor.tsx`、`TaxonomyPanel.tsx`、分类/规则表格 | `UI-CONFIG-01`～`UI-CONFIG-07` | 独立保存、移除确认、历史迁移 Tab、表格操作列 |
| `styles.css`、表格原语、列宽或响应式规则 | `UI-LAYOUT-01`～`UI-LAYOUT-04` | 浅色/深色主题、窄窗口、长文本、多按钮行 |
| `CsvImportDialog.tsx`、导入 domain/service | `UI-IMPORT-01`～`UI-IMPORT-06` | 文件结构、表头、字段映射、预览、追加/替换和不写库边界 |
| `MonthEditor.tsx`、`src/ui/month/`、保存或 dirty 状态 | `UI-MONTH-01`～`UI-MONTH-05` | 脏草稿导航、质检、保存、放弃并重载 |
| `src/ui/Analysis*`、分析 read model | `UI-ANALYSIS-01`～`UI-ANALYSIS-04` | 空状态、指标口径、相关流水弹窗和窗口范围 |
| `main.ts`、`settings.ts`、目录/备份/迁移 service | `UI-LIFE-01`～`UI-LIFE-05` | 首次配置、迁移确认/取消、恢复失败、重启和锁释放 |
| i18n、Modal、按钮、焦点或 aria | `UI-A11Y-01`～`UI-A11Y-04` | 中英文、Tab、Escape、焦点可见和读屏名称 |

## 3. 必测界面场景

以下表格是未来对话的点击入口清单。每项都写明“点击什么”和“观察什么”，不能只做静态阅读。

### 3.1 启动、导航和生命周期

| 编号 | 点击步骤 | 必须观察 |
| --- | --- | --- |
| `UI-LIFE-01` | 启动 Obsidian → 启用 Asset Track → 打开插件视图 | 无控制台启动错误；插件能显示当前状态或明确的首次配置入口；没有 Python、sidecar 或网络依赖提示 |
| `UI-LIFE-02` | 进入设置 → 选择测试数据目录 → 创建新数据库/载入数据库 | 目录仍是页面草稿；成功后才保存；失败不会把半成品路径写入设置 |
| `UI-LIFE-03` | 打开“分析 / 记录 / 配置”并返回 | 当前月份和子页上下文保持；页面切换不会悄悄丢掉未保存草稿 |
| `UI-LIFE-04` | 修改一行流水 → 点击顶部导航或切换月份 → 在确认框选择取消/放弃 | 取消留在编辑页；确认放弃后恢复 canonical 数据；没有未确认的数据库写入 |
| `UI-LIFE-05` | 关闭插件视图 → 重载 Obsidian → 重新打开同一月份 | 数据、标签、分类和最近保存状态从数据库重建；没有重复行、锁未释放或旧草稿覆盖新数据 |

### 3.2 导入账单

详细字段和异常矩阵继续参考 [临时导入 UX 清单](temporary/ux-test-checklist.md)，这里保留每次更新必须点击的主链：

| 编号 | 点击步骤 | 必须观察 |
| --- | --- | --- |
| `UI-IMPORT-01` | 记录 → 流水 → 导入账单 → 选择 CSV/XLSX/XLS | 先确认文件结构、编码、分隔符、工作表和表头；没有直接写库动作 |
| `UI-IMPORT-02` | 选择候选表头 → 确认 → 下一步确认字段 | 表头行号和原始内容正确；必填字段、可选字段和收支映射清楚分组 |
| `UI-IMPORT-03` | 修改日期/金额/收支/状态映射 → 生成预览 | 接受、过滤、错误和警告数量随映射变化；过滤原因可解释；零接受行不能应用 |
| `UI-IMPORT-04` | 选择“追加”或“替换” → 完成并加入草稿 | 只进入当前月份草稿；反馈明确“尚未写入数据库”；追加不自动去重，替换明确清除范围 |
| `UI-IMPORT-05` | 导入后修改一行 → 保存流水 → 关闭并重开月份 | 来源、原始行号、分类和金额保存正确；保存失败时不出现半保存状态 |
| `UI-IMPORT-06` | 生成预览后返回上一步或关闭弹窗 | 旧预览不会被误应用；取消不改变当前草稿；Escape 和关闭按钮都可用 |

### 3.3 流水、标签和批量操作

| 编号 | 点击步骤 | 必须观察 |
| --- | --- | --- |
| `UI-TXN-01` | 记录 → 流水 → 依次点击出账、入账、理财；再点击逐项、按商品汇总、按交易对手汇总 | Tab 数据隔离；理财不出现标签入口；三种视图仍指向同一原始流水 ID |
| `UI-TXN-02` | 在已有标签的出账/入账行点击“编辑标签” | 弹窗显示已有标签名称；已关联标签复选框为选中；取消不改变草稿。此项是标签空弹窗的固定回归点 |
| `UI-TXN-03` | 在标签弹窗取消 → 再打开 → 勾选/取消标签 → 点击“应用到草稿” | 选项只进入当前草稿；行内标签 chip 更新；没有应用按钮时不应写库 |
| `UI-TXN-04` | 勾选多条流水 → 添加/移除/替换标签 → 查看预览 → 确认或取消 | 预览展示影响数量和冲突；取消无变化；确认后仍需点击“保存流水” |
| `UI-TXN-05` | 修改一条流水 → 点击“放弃并重载”或切换月份 → 选择确认 | 草稿恢复数据库版本；标签、分类、金额和来源一起恢复；没有只恢复部分字段 |

标签回归必须用“已有标签”的 fixture，不能只用空标签数据库；至少验证一个选中项、
一个未选中项和没有可选项的空状态。

### 3.4 配置、分类属性和标签定义

| 编号 | 点击步骤 | 必须观察 |
| --- | --- | --- |
| `UI-CONFIG-01` | 配置 → 分类定义 → 直接修改分类名称/定义说明/收支/颜色 → 保存分类 | 表内字段均能保存；属性和标签未被一并提交；成功后刷新仍保留修改 |
| `UI-CONFIG-02` | 配置 → 分类属性 → 左栏新增/修改属性组或属性值 → 点击左栏“保存属性” | 属性区域独立保存；右栏标签草稿不被提交；保存反馈明确 |
| `UI-CONFIG-03` | 配置 → 分类属性 → 右栏新增/修改标签 → 点击右栏“保存标签” | 标签区域独立保存；重新打开流水标签编辑时读取最新定义并预选已有标签；颜色、名称和 active 状态一致 |
| `UI-CONFIG-04` | 对已被引用的属性/标签点击“移除” | 确认框只说明将要移除及下一步选项，不展示 sha、完整路径、月份明细等内部冗余信息 |
| `UI-CONFIG-05` | 在移除确认中分别选择取消、清理引用、转移后移除 | 取消无变化；清理/转移显示预览和冲突；确认后单事务完成，失败不覆盖当前数据库 |
| `UI-CONFIG-06` | 打开分类编辑 → 切换“分类 / 属性 / 标签 / 历史迁移”相关 Tab | Tab 只显示当前内容；历史迁移与分类属性处在同一行；不再出现无作用的重复关闭按钮 |
| `UI-CONFIG-07` | 修改左右分栏后切换配置子页或离开配置页 → 在未保存提示中选择保存、取消或放弃 | 两侧保存边界独立；放弃操作恢复实际 dirty 区域；未保存提示只对应实际 dirty 区域 |

### 3.5 数据健康、商品总览和历史迁移

| 编号 | 点击步骤 | 必须观察 |
| --- | --- | --- |
| `UI-RULE-01` | 配置 → 数据健康；查看冲突、未覆盖和正常商品组 | 每行列数一致；空状态、长商品名和多行分类不会改变表格列结构 |
| `UI-RULE-02` | 在数据健康表头找到“操作” → 对比多行操作按钮的横向位置和垂直位置 | “操作”表头、每行操作单元格属于同一列；按钮在单元格内居中；行高变化不会把按钮挤到上一行或下一行 |
| `UI-RULE-03` | 配置 → 商品总览 → 按商品/按交易对手切换 → 查看操作列 | 切换分组后仍保持相同列数和操作列宽；商品、交易对手、规则和分类编辑入口不会因为布局修复消失 |
| `UI-RULE-04` | 点击数据健康/商品总览中的“编辑分类”或具体商品 → 打开历史详情 | 详情弹窗加载正确商品组和月份；分类修改有预览、确认和 revision 校验；关闭不产生写入 |
| `UI-RULE-05` | 在历史详情进入迁移历史 → 查看 Tab、返回、取消和确认 | 迁移历史是与分类属性同一行的 Tab；无无作用关闭按钮；确认前能看到影响摘要，确认后一次事务提交 |
| `UI-RULE-06` | 在一个有部分覆盖/冲突的商品组点击规则或分类操作 | 规则覆盖、冲突和分类状态与实际流水数量一致；不会把整个商品组错误标记为全部覆盖 |

当前两项最近修复的固定回归点是 `UI-RULE-02` 和 `UI-TXN-02`。其他对话接手时，
即使只改了 CSS 或 Modal，也应至少重新执行这两项。

### 3.6 月度工作台、资产和分析

| `UI-ANALYSIS-04` | 以窄窗口、深色主题打开月度和年度分析 | 图表、指标卡、表格和说明不重叠；关键数值和异常颜色仍可读 |

| 编号 | 点击步骤 | 必须观察 |
| --- | --- | --- |
| `UI-LAYOUT-01` | 在浅色/深色主题分别打开数据健康、商品总览、流水和标签弹窗 | 表格边界、按钮、标签 chip、错误和成功状态有足够对比；没有白块或文字被主题吞掉 |
| `UI-LAYOUT-02` | 将窗口缩到窄面板；滚动数据健康、商品总览和逐项流水 | 表头与正文仍对应；操作列可点击；长文本换行不会改变列语义或遮住按钮 |

| `UI-A11Y-01` | 只用 Tab/Shift+Tab 浏览主导航、表格操作和弹窗 | 焦点顺序符合页面顺序，焦点始终可见，不跑到遮罩后；Enter/Space 可执行按钮 |

| `UI-A11Y-03` | 使用中文和英文界面打开本轮修改涉及页面 | 标题、按钮、状态、错误、空状态和 aria label 都有对应语言，不出现空白或 `undefined` |
| `UI-A11Y-04` | 用辅助技术/AX tree 检查表格和 Modal | 表头、行、操作列、标签复选框和选中状态可被读出；错误字段有 `aria-invalid` 或等价说明 |

### 4.1 失败时的 debug 顺序

1. 先固定当前窗口、月份、fixture 和构建版本，不立即重载到另一版本；
2. 记录触发按钮、弹窗标题、表头/行结构、Notice 和控制台异常；
3. 检查最终安装文件是否与本次 `build/` 一致，再判断是否为缓存问题；
4. 区分“数据没有传入”“弹窗过滤掉了”“CSS 影响布局”“Modal 被宿主字段覆盖”“保存事务失败”；
5. 用最小 fixture 重复，避免用整库数据掩盖边界；
6. 只有在失败证据保存后才修改代码；修复后重新执行原场景和受影响路由表中的相邻场景；
7. 若意外改动真实数据、数据库、备份或 Vault，立即停止并报告，不继续覆盖现场。

### 4.2 通过条件

一个 UI 修复只有同时满足以下条件，才能交给下一轮对话继续优化或写入 release 日志：

- 自动门禁通过；
- 最终构建已加载并重载到实际 Obsidian；
- 受影响场景完成规定点击；
- 至少验证成功、取消/放弃和重载后的一个路径；
- 没有新增控制台错误、残留 debug Notice 或临时诊断文本；
- 测试记录包含环境和脱敏证据；
- 没有把未测试的迁移、保存、回滚或跨平台结果写成通过。
