# 12 Asset Track 产品理念

> 文档角色：开发与维护。这里定义长期产品方向，不是用户操作手册；用户阅读请从
> [README](../README.md) 或[用户指南](02-user-guide.md)开始。

## 1. 我们要解决的问题

用户的财务数据本来已经存在于微信、支付宝、银行卡和其他支付平台中，但传统记账
要求用户再次逐笔录入、判断和维护。问题不是少一个快捷按钮，而是：

- 每笔消费都要打断日常生活；
- 长期高频记录依赖注意力和自律，难以持续；
- 多个平台、多张表和多份笔记容易产生不一致；
- 图表很多，不代表输入完整、口径统一、结论可信。

Asset Track 的目标是减少这些重复劳动，让用户把时间留给少量真正需要判断的事项。

## 2. 产品定位

> **Asset Track 不需要成为更方便的手工记账工具。它应当成为一个以月度账单导入
> 为入口、以统一 SQLite 数据库为唯一事实、以资产闭环验证数据质量、由用户完全
> 私有控制的个人财务结算系统。**

面向用户的承诺可以更简单地说成：

> **每月花一点时间整理已经存在的账单，就能持续了解钱去了哪里、资产发生了什么变化，
> 并知道这些结论是否完整可信。**

Obsidian 是本地宿主和交互载体，不是产品价值本身。产品价值来自月度结算、统一事实、
数据验证和用户控制。

Asset Track 记录的不是所有资金移动，而是个人经济活动如何发生、如何结算，以及
月底还有哪些关系尚未结清。它追求的是足以解释个人经济活动、未结关系和月末资产
状态的最小事实集合，而不是完整复制银行、支付平台或投资账户里的每一次内部流转。

## 3. 用户工作模型

```text
日常：正常支付，不增加实时记账任务
月末：导出并集中导入账单
整理：系统处理重复工作，用户处理异常和冲突
验证：补充资产状态，用流水与资产变化检查完整性
理解：查看月度、年度和资产变化，形成自己的判断
```

这意味着“每月一次”是产品方法，而不是功能限制。系统不以每天打开次数、连续打卡
或手工记录条数衡量成功。

## 4. 结算语义模型

个人财务活动可以拆成两个时点：

```text
经济关系发生
     ↓
现金最终结算
```

大多数支出、收入、加仓和提现属于即时结算：经济关系和现金结算同时完成。代付和
借款则属于延迟结算关系：现金已经先发生，人与人之间的结算关系稍后才完成。

代付和借款应统一认知，但不统一模型：

| | 代付 | 借款 |
| --- | --- | --- |
| 本质 | 消费结算 | 纯资金结算 |
| 是否存在消费归属 | 有 | 无 |
| 是否影响真实消费 | 是 | 否 |
| 通常金额/周期 | 小、短 | 可大、可跨月 |
| 是否需要持续追踪余额 | 不需要 | 需要 |
| 最终处理 | 抵扣支出 | 消除债权/债务 |
| 当前模型 | Transaction | DebtRecord |

因此，短期、小额、依附消费的待结算关系用流水修正；独立、持续、与消费无关的待
结算关系用状态事实追踪。代付是一种消费型延迟结算：现金回流，但不产生收入，而是
归还此前由用户暂时承担的消费金额，因此冲减实际支出。借款是双向待结算头寸：既可
表示我借入、待偿还，也可表示我借出、待收回。

Asset Track 是月度现金结算制，不是严格的权责发生制。系统保留现金账单发生月份的
真实性，不为了追求会计期间归属而重写历史流水；对影响资产闭环的重要跨期关系，
通过借款等独立状态事实补充表达。

## 5. 两个并行设计目标

### 降低负担

- 不要求每次消费后立即记账；
- 账单导入是主要入口，常用映射可以复用；
- 稳定、重复的分类工作交给规则；
- 用户优先处理未分类、冲突、缺口和异常；
- 月度流程有明确的开始、检查和完成感。

### 增强掌控

- 用户知道本月导入了什么、还缺什么；
- 用户知道数字如何计算、异常来自哪里；
- 批量修改先展示影响范围，再由用户确认；
- 自动建议不会静默改写历史事实；
- 数据可以备份、恢复和迁移，始终留在用户控制的本地环境。

中心原则是：

> **系统承担重复整理，用户保留最终判断；界面隐藏不必要的复杂度，同时让证据始终可查。**

同等级原则是：

> **只记录有解释价值的财务事实，不追求完整复制所有资金移动。**

即时结算用流水表达；短期消费型延迟结算用流水修正；需要跨月持续追踪的纯资金关系
用有方向的结算头寸表达。

## 6. 六条设计原则

### 每月集中，避免持续打扰

围绕月度结算组织首页、导入、异常和分析，不把实时记账做成主流程。

### 导入优先，手工补充

账单导入负责主要数据获取。手工流水用于现金消费、账单缺失、特殊交易和纠错。

规则不是一次性配置出来的，而是从真实账单中生长出来的。用户导入一个月账单后，
通过流水的逐项、商品汇总和交易对手汇总视图，并按流水数量排序，就能发现大量重复
项目并批量创建规则；连续几个月后，稳定商户、商品和代付回款会沉淀成个人规则集，
让之后每次账单导入都更有价值，也更容易看清资产流向。

### 一个事实源

账户、流水、借款、理财、固定资产、分类和规则进入同一个本地事实层。图表、Markdown、
缓存、导出和界面草稿都不能形成第二套账本。

### 最小事实集合

只记录对月度结算、未结关系、资产闭环或长期分析有解释价值的事实。不记录内部转账，
不追踪证券每次成交，不做信用卡复式账户；固定资产只登记状态，不每日估值。

### 例外优先

系统自动处理稳定、重复的工作，把未分类、规则冲突、日期或金额异常、导入缺口和
资产对账差额交给用户判断。

### 每个数字可解释

月度、年度、商品、分类和资产指标使用统一定义，并尽量能回到具体流水和输入来源。

### 数据由用户控制

存储、备份、恢复、迁移和删除由用户决定；不要求账户，不依赖云端分类或银行授权，
不把未经确认的建议写成财务事实。

## 7. 产品边界

以下方向应降级或排除：

- 高频快速记账、每日预算、实时余额提醒和连续打卡；
- 云端银行同步、多用户服务和联网分类；
- 为每个平台建立独立交易表、计算口径或分析页面；
- 用自动分类掩盖导入缺口、规则冲突或资产差额；
- 让 Markdown、图表、缓存、导出或 AI 输出成为第二套财务账本；
- 让复杂功能破坏月度工作流的清晰度；
- 为小额代付建立完整应收余额、原始消费关联、部分结算和跨月回溯重算；这会把月度
  现金结算制复杂化为权责发生制系统。

当前的实验性 AI 分类只能提出分类、交易对手或商品重写建议；它只处理用户选中的流水，
不会创建永久规则，也不会绕过预览、用户确认和统一 SQLite 保存事务。用户不配置 AI 时，
普通导入、规则和手工编辑完全不受影响。

## 8. 产品术语

| 推荐术语 | 含义 |
| --- | --- |
| 月度结算 | 完成一个月财务整理、验证和分析的完整过程 |
| 账单导入 | 从支付平台获取流水的主要方式 |
| 数据源 | 微信、支付宝、银行卡或其他账单来源 |
| 财务事实 | 已经校验并保存到本地 SQLite 的数据 |
| 统一规范 | 把不同平台字段映射到稳定的内部语义 |
| 即时结算 | 经济关系和现金结算在同一时点完成 |
| 延迟结算 | 经济关系先发生，现金或人与人关系稍后才结清 |
| 代付回款 | 消费型延迟结算的现金回流，冲减支出，不等于收入 |
| 待结算头寸 | 借入或借出形成的未结纯资金关系 |
| 数据健康 | 数据完整性、分类、冲突和覆盖情况 |
| 对账 | 用资产变化检查流水是否完整 |
| 手工补录 | 处理导入范围外的少量记录 |

用户文案优先使用“每月整理”“账单导入”“检查完整性”等直观说法；schema、revision、
Repository、WAL 等术语只出现在开发和维护文档中。

## 9. 功能决策检查表

新功能进入开发前，至少回答以下问题：

1. 它降低了收集、整理、补充、验证或完成月度结算的哪一种成本？
2. 它是否仍然进入统一事实层，而不是创建第二套数据？
3. 它是否让异常、覆盖、冲突或资产闭环更可见？
4. 它的指标是否复用统一领域计算，并能解释到事实记录？
5. 它是否保留用户确认、备份恢复、私有存储和可逆修改？
6. 它记录的是有解释价值的财务事实，还是只是复制一次平台资金移动？
7. 它属于消费、收入、投资还是纯资金传递；结算是否延迟；是否需要跨月状态？

如果只能回答“让用户多做一次手工录入”或“增加一个独立统计数字”，就不应成为优先
方向。

## 10. 当前能力与后续目标

当前已具备：月度账单导入、统一 SQLite 事实层、分类与通用规则治理、批量预览和操作审计、
资产与对账分析、可选 AI 分类、本地备份恢复和异常保存提示。

后续目标是把这些能力组织成更清晰的月度结算工作台，并逐步加入导入批次、数据源
覆盖、重复风险、数据健康和指标下钻。目标能力必须在实现前明确标注，不能写成当前
已经存在的用户功能。

借款领域未来最自然的扩展是部分结算：保留一条借款事实，并在其下记录还款或收回明细，
计算剩余头寸。它不应扩展成银行贷款系统；只有当真实使用中频繁出现部分偿还、跨月收回
或多次结清时，才值得进入设计。
