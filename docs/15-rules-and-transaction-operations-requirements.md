# 15 规则、流水聚合与批量操作需求

1. 当前界面锚点

当前编辑器的顶层结构保持不变：

```text
分析 / 记录 / 配置
```

当前二级结构如下：

| 区域         | 当前子页面或视图                                    | 本需求的目标变化                                                       |
| ------------ | --------------------------------------------------- | ---------------------------------------------------------------------- |
| 记录         | 资产账户 / 流水 / 借款 / 固定资产                   | 只重组“流水”内部，不拆出新的顶层页面                                 |
| 记录 → 流水 | 逐项 / 按商品汇总；支出、收入、代付、加仓、提现分块 | 增加出账 / 入账 / 理财 Tab，并统一逐项、商品汇总、交易对手汇总三种视图 |
| 配置         | 数据健康 / 分类定义 / 匹配规则 / 商品总览           | 规则中心泛化；商品总览复用商品与交易对手汇总；分类定义增加描述         |
| 设置         | 数据目录、备份、金额格式等                          | 增加 AI 分类配置；API Key 只放 Obsidian SecretStorage                  |

现状与目标的关键差异：当前规则解析只使用“收支类型 + 商品”，交易对方只在流水和
历史详情中展示；本专项需求将交易对方纳入规则条件，但不改变顶层导航、统一 SQLite
事实源、月度草稿与 revision 保存边界。

本文统一使用当前界面的“交易对手”作为字段和 UI 术语；原清单中的“商户”与“商户规则”
均对应“交易对手”与“交易对手规则”。

## 2. 统一产品边界

以下约束适用于本文件所有功能：

1. 流水、分类和有效规则仍只有一套事实来源。商品汇总、交易对手汇总、规则覆盖和
   AI 预览都是从同一批原始流水派生，不创建独立统计账本。
2. “支出”和普通“收入”是可分类流水。代付归入“入账”Tab，但不属于普通收入，
   不显示分类控件，也不参与分类规则和 AI 分类；加仓、提现归入“理财”Tab。
3. 继续保留收支类型作为规则的固定维度。同名商品或交易对手在支出、收入中可以
   分别配置规则；规则唯一性在同一收支类型内判断。
4. 规则编辑、规则应用、批量修改、分类回写、商品或交易对手统一、收入与代付转换
   都必须先预览影响，再由用户确认写入。
5. 修改规则定义不会自动改写历史流水。规则变化只影响未来新流水，以及用户在当前
   草稿或选中范围内明确执行的“应用规则”操作。
7. 规则和 AI 都不能绕过现有 Service、Repository、revision 和事务写入边界。AI
   只能产生待确认建议，不能直接写入财务事实。
8. 不改变现有财务计算口径、特殊流水的分类排除规则和固定资产边界。

## 3. 优先级与实现先后

### 3.1 优先级总表

| 优先级     | 目标                                                 | 依赖                       | 完成标志                                           |
| ---------- | ---------------------------------------------------- | -------------------------- | -------------------------------------------------- |
| P0         | 规则模型、匹配解析、冲突校验、操作范围和预览契约     | 无                         | 规则结果在所有入口一致，非法规则不能保存           |
| P0         | 批量操作日志、成功/失败/跳过和前后对比               | P0 操作范围                | 每次高影响修改都能回看具体结果                     |
| P1         | 记录 → 流水的三类业务 Tab、三种视图和多选           | P0                         | 原始流水、汇总组和选择范围能稳定互相映射           |
| P1         | 通用规则创建/编辑 Modal、规则中心和商品/交易对手汇总 | P0                         | 所有入口使用同一规则字段、优先级和影响预览         |

| P1         | 收入与代付的类型转换                                 | 批量操作与审计日志         | 转换影响统计，且可追溯、可撤销或按历史回写策略处理 |
| P2         | AI 分类设置、预览、确认、重试和审计                  | P0、P1 选择/预览、分类描述 | AI 只是实验性建议层，不产生永久规则                |
| P3（未来） | 代付与支出的多对多关联、部分代付和个人承担额         | 新的关系模型与统计口径     | 关联、拆分、解除和统计全部可追溯                   |

### 3.2 底层到 UI 的实施顺序

1. **冻结业务模型**：确定流水类型、规则收支维度、规则作用域、规范化方式、临时
   保护范围和操作日志字段。
2. **实现规则领域契约**：完成三种匹配作用域、固定优先级、单次命中、重写语义、
   冲突检查和重写链检查。
3. **实现写入前契约**：所有批量、规则、转换和 AI 回写统一产生预览；Repository
   重新校验目标 ID、分类、规则 revision、月份 revision 和影响数量，并在单事务中
   写入。
4. **实现读取模型**：为逐项、商品汇总、交易对手汇总、规则命中解释、影响范围和
   操作日志提供稳定的原始流水 ID 映射。汇总只读已保存事实，当前月份操作另带草稿。
5. **实现通用规则 Modal 与规则中心**：先让规则创建、编辑、删除和冲突反馈在一个
   入口内稳定，再接入流水和各类汇总页面。
6. **重组记录 → 流水 UI**：加入出账、入账、理财 Tab，多选、全选/全不选、三种视图
   和批量操作结果窗口。
7. **扩展配置 → 商品总览**：加入交易对手汇总，并复用与流水相同的汇总、选择和规则
   影响组件。
8. **最后接入 AI**：配置、调用、解析、失败重试和审计均建立在已有选择、预览、
   分类描述和普通保存路径上。
9. **另行设计代付关系模型**：P3 之前不增加关联关系表、不改变个人承担额统计，
   不把未来模型混入本轮流水 UI 实现。

## 4. P0：规则与批量操作的底层契约

### 4.1 规则数据模型

每条有效规则至少包含以下业务字段：

| 分组     | 字段                 | 约束                                                   |
| -------- | -------------------- | ------------------------------------------------------ |
| 标识     | 规则编号             | 使用稳定的规则 ID；在规则表和流水详情中可见            |
| 固定维度 | 收支类型             | 支出或收入；不允许用户把代付、加仓、提现配置为分类规则 |
| 匹配条件 | 匹配范围             | 仅商品、仅交易对手、交易对手 + 商品                    |
| 匹配条件 | `counterparty`     | 精确匹配条件；仅商品规则为空                           |
| 匹配条件 | `product`          | 精确匹配条件；仅交易对手规则为空                       |
| 匹配结果 | `category_key`     | 必须指向启用的同收支类型分类                           |
| 匹配结果 | `rewrite_merchant` | 可选；空值或纯空格表示不修改                           |
| 匹配结果 | `rewrite_product`  | 可选；空值或纯空格表示不修改                           |

业务层可将匹配范围表示为 `product`、`merchant`、`merchant_product`。数据库字段命名
和迁移方式在技术设计阶段确定，但不能丢失已有规则 ID、收支类型和分类 key。

规则不提供以下能力：

- 用户自定义优先级；
- 正则、关键词、包含、模糊匹配或自定义表达式；
- 通配符条件；
- 通过规则把交易对手或商品清空。

“精确匹配”允许沿用现有的规范化边界，例如去除首尾空格、压缩连续空白和统一比较
大小写；规范化只是为了稳定比较，不得演变成包含或模糊匹配。

### 4.2 规则解析与固定优先级

对一笔可分类流水，只用原始的交易对手、商品和收支类型解析一次：

1. 交易对手 + 商品规则；
2. 商品规则；
3. 交易对手规则。

第一层命中后，不再考虑低优先级规则。一笔流水每次最多采用一条规则。只有最终被
采用的规则可以同时执行：

1. 写入目标分类；
2. 重写交易对手（如有非空输出）；
3. 重写商品（如有非空输出）。

重写结果不触发第二轮规则匹配。规则更新只在下一次显式应用或新流水进入时使用；
当前草稿重新计算必须是用户明确执行的操作，不由保存规则时静默触发。

### 4.3 规则冲突、唯一性与重写链

#### 硬冲突

在同一收支类型、同一匹配范围、同一规范化条件下：

- 只能有一条有效规则；
- 创建或编辑保存时直接阻止；
- 明确展示已有规则编号、匹配条件和目标分类；
- 用户只能修改已有规则、改变条件，或取消创建。

数据库唯一约束、Repository 校验和领域校验都必须覆盖以下三类键：

1. 收支类型 + 交易对手；
2. 收支类型 + 商品；
3. 收支类型 + 交易对手 + 商品。

唯一性按规范化后的精确条件判断；空条件不能形成可用规则。

#### 正常覆盖

不同匹配范围即使命中不同分类，也不是冲突。例如交易对手规则和商品规则同时命中
时，按固定优先级选择结果，并在流水详情中说明“组合规则 / 商品规则 / 交易对手规则”
的覆盖关系。数据健康可以展示覆盖统计，但不能把这种正常覆盖标成冲突。

#### 重写链检查

保存规则前，系统必须用候选规则模拟重写后的交易对手和商品：

- 如果规则 A 的输出会让重写后的值再次命中规则 B，且 B 不是同一条稳定规则，视为
  潜在二次匹配链；
- 潜在二次匹配链和循环链均禁止保存，并显示涉及的规则编号和字段；
- 运行时仍只做一轮匹配，不能依赖“禁止保存”以外的隐式循环保护；
- 空值、纯空格和“不修改”输出不参与重写链构造；
- `rewrite_merchant` 和 `rewrite_product` 都不能通过规则清空原字段。

### 4.4 规则变更对草稿与历史的影响

| 操作             | 当前月份未保存草稿                                 | 已保存历史流水             | 新导入或未来显式应用 |
| ---------------- | -------------------------------------------------- | -------------------------- | -------------------- |
| 修改规则目标分类 | 用户明确重新计算后进入草稿；不在保存规则时静默改动 | 不变化                     | 使用新分类           |
| 修改重写字段     | 用户明确重新计算后进入草稿；不在保存规则时静默改动 | 不变化                     | 使用新重写结果       |
| 删除规则         | 不自动回写                                         | 不自动回写                 | 不再命中             |
| 直接修改历史分类 | 仅在历史迁移/批量修改明确确认后写入                | 按所选流水和 revision 写入 | 不改变规则本身       |

### 4.5 选择范围与批量操作契约

选择状态以原始流水的稳定 ID 为准，不以表格行号或汇总行号为准。

- 逐项视图选择一笔或多笔原始流水；
- 商品汇总组被选中时，展开为该组包含的全部原始流水；
- 交易对手汇总组被选中时，展开为该组包含的全部原始流水；
- “全选”和“全不选”作用于当前 Tab、当前筛选和当前视图可操作范围；
- 切换视图不会改变事实数据，选择集合仍映射到原始流水；切换月份或业务 Tab 时，
  必须避免把不可分类或不适用的流水误带入操作；
- 规则应用、批量编辑、转换和 AI 都先生成预览，预览必须显示总数、实际变更数、
  跳过数、失败数和至少一组前后对比；
- 写入后记录操作日志，并提供查看具体成功、失败和跳过流水的入口。

操作日志至少包含：操作编号、操作时间、操作用户、操作类型、来源页面、业务 Tab、
选择范围、成功/失败/跳过数量、前后字段值、失败原因、使用的规则编号或 AI 批次编号。
日志是追溯元数据，不得参与财务统计。

## 5. P1：记录 → 流水页面

### 5.1 页面结构

继续使用一个“流水”子页面，不拆成三个独立页面。页面内部改为：

```text
流水
├── 出账：支出
├── 入账：收入、代付
└── 理财：加仓、提现
```

三个 Tab 复用列表、编辑、选择、预览、保存和日志逻辑，只根据业务类型展示适用字段：

- 出账：支出，显示分类；
- 入账：收入显示分类；代付归入入账，但不显示分类，也不计入普通收入统计；
- 理财：加仓和提现，不显示分类，也不显示分类规则和 AI 分类入口。

导入账单、月份选择、放弃并重载、保存流水仍属于流水区块的页面级操作；批量操作按钮
放在当前业务 Tab 的上下文工具栏，不再把所有动作堆在整个页面的一个顶部按钮区。

### 5.2 三种流水视图

每个适用 Tab 都支持以下视图，三种视图使用同一份草稿和同一批原始流水：

1. **逐项视图**：一行一笔流水；
2. **按商品汇总**：一行一个商品组；
3. **按交易对手汇总**：一行一个交易对手组。

汇总只改变展示和选择方式，不创建统计事实，也不改变保存粒度。汇总行展开后，编辑
的仍是对应原始流水。

### 5.3 逐项视图

逐项流水至少展示：行号、日期、交易对手、商品、金额、分类（仅支出/收入）、规则编号、
操作。

- 命中规则时显示最终采用的规则编号；存在候选覆盖时同时提供规则级解释；
- 无命中显示“无规则”，硬冲突显示冲突规则编号，不静默选择；
- 每行提供“新增规则”入口，打开统一的新建规则 Modal，并以当前行的收支、交易对手、
  商品和分类作为初始值；
- 规则创建成功后不自动改写历史流水，当前月份是否重新应用由用户明确选择；
- 理财与代付行不显示分类、规则或 AI 分类控件；
- 大列表继续使用可视行渲染，选择和规则编号必须以稳定流水 ID 关联。

### 5.4 商品汇总视图

商品汇总至少展示：

1. 商品名称；
2. 流水数量；
3. 总金额；
4. 分类分布；
5. 交易对手数量；
6. 未分类数量；
7. 已有商品规则及覆盖状态；
8. 批量操作入口。

商品组可以被整体选择，也可以展开后选择具体流水。创建规则前必须显示：当前月份和
历史已保存月份中会被该条件命中的流水数量、涉及月份、现有分类分布，以及本次规则
创建不会自动回写历史的说明。

### 5.5 交易对手汇总视图

交易对手汇总至少展示：

1. 交易对手名称；
2. 流水数量；
3. 总金额；
4. 商品数量；
5. 分类分布；
6. 分类纯度；
7. 未分类数量；
8. 已有交易对手规则及覆盖状态；
9. 被商品规则覆盖的流水数量；
10. 批量操作入口。

“分类纯度”只作为汇总解释指标，不作为自动选类依据。交易对手组创建规则前同样必须
显示实际影响范围，并区分“当前可显式应用的流水”和“历史潜在覆盖但不会自动改写的
流水”。

### 5.6 流水页的操作模式

#### 普通模式

- 出账和入账 Tab 提供“应用规则”；
- 默认作用范围是当前月份全部可分类流水，即支出和收入流水，而不是当前可见的一行；
- 执行前预览必须说明会跨出账/入账两个 Tab 处理多少笔；
- 理财 Tab 不显示或禁用该操作；
- 应用结果先进入当前月份草稿，用户仍需确认并保存流水。

#### 批量选择模式

- 用户进入选择模式后，可以使用“全选”和“全不选”；
- “应用规则”只作用于选中的可分类流水；
- “AI 分类”只作用于选中的可分类流水；
- 修改交易对手、修改商品、修改分类和创建规则均只作用于选中范围；
- 选择商品组或交易对手组等同于选择该组的全部原始流水；
- 当前操作可以选择跳过本次保护范围，默认不覆盖保护范围；用户必须明确选择后才可
  纳入；保护范围不形成持久化锁定。

### 5.7 批量操作清单

批量工具栏支持：

- 修改交易对手；
- 修改商品；
- 修改分类；
- 创建规则；
- 应用已有规则；
- 使用 AI 分类；
- 收入转为代付；
- 未关联代付转回收入。

批量修改前统一展示影响数量、目标值、原值分布和前后预览。操作结束后展示成功、失败、
跳过数量，并从结果入口查看具体流水和原因。

### 5.8 收入与代付转换（当前阶段的有限范围）

本阶段只实现交易类型转换，不实现代付与支出的关联关系：

1. 导入账单时，收到的代付款仍先按普通收入导入，不要求用户预先修改 CSV；
2. 收入流水提供“转为代付”；
3. 代付流水提供“转回收入”；
4. 支出、加仓、提现不提供这两个转换入口；
5. 转为代付后从普通收入统计中移除，转回后恢复普通收入统计；
6. 保留原流水 ID、导入来源字段和操作前后对比；
7. 转换前后都要显示影响月份、金额和分类适用性；
8. 在完整代付关联模型完成前，关联支出的入口只能显示为后续能力说明，不能伪装成
   已经建立了关联。

完整的关联、部分代付和个人承担额见第 8 节，当前不作为本阶段完成条件。

## 6. P1：配置中心与规则工作台

### 6.1 配置 → 分类定义

分类表增加可编辑的 `description` 字段，用于描述分类的定义、边界和典型例子。

- 描述是分类元数据，不是某一笔流水的 AI 结果；
- 用户可以直接编辑，保存时沿用分类 revision 和现有分类校验；
- 分类描述用于 AI 输入，也可在规则创建和分类选择处作为辅助说明；
- 修改描述不自动改写历史流水和规则结果；
- `description` 是分类定义的正式新字段，必须作为 `category_definitions` 的持久化字段，
  不得仅保存为 AI 配置或按 `category_key` 维护一份并行的插件本地元数据；该变更纳入
  schema 10。

### 6.2 配置 → 匹配规则

规则表需要从“商品规则表”升级为通用规则表。推荐列顺序如下：

```text
规则编号
→ 匹配条件：交易对手、商品、匹配范围、收支类型
→ 匹配结果：重写交易对手、重写商品、目标分类
→ 规则状态、命中数量、最后使用时间、操作
```

具体布局规则：

- 匹配条件列在匹配结果列之前；
- 条件输入和结果重写使用输入框，选择型字段使用下拉框；
- 在同一分组内，文本输入框先于下拉框；
- 目标分类下拉框只展示同收支类型的启用分类；
- 固定优先级以说明或只读标签展示，不提供用户拖拽或编辑优先级；
- 规则编号、冲突状态、命中数量和实际覆盖范围可直接查看；
- 规则行编辑和 Modal 创建使用同一字段定义，不能出现一处支持重写、另一处不支持的
  分叉。

规则操作要求：

1. 支持新增、编辑、保存和删除；
2. 相同作用域、相同条件的硬冲突在保存前阻止，并给出已有规则编号；
3. 不同作用域的正常覆盖显示为优先级关系，不进入硬冲突弹窗；
4. 删除规则前检查使用次数和审计价值；存在已命中流水时弹窗说明不建议删除，用户
   可以取消或确认；确认后在保存事务中真正删除；
5. 规则表中的规则编号与流水详情、操作日志中的编号一致；
6. 规则保存前执行重写链静态检查。

### 6.3 通用新建/编辑规则 Modal

流水逐项行、流水商品汇总、流水交易对手汇总、配置商品总览和配置交易对手总览都使用
同一个规则 Modal。Modal 至少提供：

1. 匹配范围：仅商品、仅交易对手、交易对手 + 商品；
2. 收支类型；
3. 商品和交易对手条件；
4. 目标分类；
5. 重写交易对手；
6. 重写商品；
7. 规则实际影响预览；
8. 冲突、重写链和无效分类提示；
9. 保存或取消。

从某笔流水或汇总组进入时，Modal 预填当前值，但用户仍可修改匹配范围和结果。创建规则
不等同于应用规则；创建成功后是否在当前月份执行应用，必须由用户另行确认。

### 6.4 配置 → 商品总览

商品总览保留长期历史统计，并增加内部 Tab：

```text
商品总览
├── 按商品汇总
└── 按交易对手汇总
```

两个 Tab 使用同一套汇总与选择契约：

- 支持按收支、分类、商品、交易对手和时间筛选；
- 可直接填充交易对手、商品和已有分类；
- 可批量统一商品或交易对手，但写入前必须按流水 ID 生成预览和月份 revision；
- 可以从分组创建规则；
- 创建规则前显示历史覆盖数量、涉及月份、分类分布和当前规则覆盖情况；
- 历史汇总只读已保存月份，当前草稿不伪装成历史事实；
- 规则创建只影响未来和后续显式应用，不自动改写历史；
- 商品规则、交易对手规则和组合规则的覆盖关系必须使用与流水页相同的解析结果。

### 6.5 配置 → 数据健康

数据健康在现有商品-分类问题之外，至少能定位：

- 同一作用域、同一条件的规则硬冲突；
- 规则重复或历史兼容数据导致的无效规则；
- 重写链风险；
- 规则未覆盖、部分覆盖和被更高优先级规则覆盖的数量；
- 商品或交易对手汇总中的未分类与分类混合情况。

正常的跨作用域覆盖不作为冲突，但应能在规则解释和汇总指标中被看见。

## 7. P2：AI 分类

AI 分类是实验性功能，必须在普通规则、选择和预览链路稳定后再接入。

### 7.1 配置位置与隐私边界

AI 配置只放在 Obsidian 插件设置页的独立区域，不增加新的顶层主导航。设置包括：

- API 地址；
- 模型名称；
- 超时时间；
- API Key 使用 Obsidian SecretStorage 保存。

API Key 不写入插件普通设置、SQLite、流水、规则或操作日志。界面必须明确：

1. AI 分类为实验性功能；
2. 分类质量取决于模型能力，建议使用指令理解和结构化输出能力较强的模型；
3. 选中的流水会发送到用户配置的第三方 API；
4. 用户可以不配置 AI，也不影响普通导入、规则和手工编辑。

### 7.2 AI 输入

每笔 AI 请求至少包含：

- 交易对手；
- 商品；
- 可选的当前分类信息；
- 所有可用分类的名称；
- 分类定义 `description`；
- 分类标识 `category_key`；
- 当前收支类型。

只发送当前选中的可分类流水和完成分类所需的最小字段，不发送 API Key、数据库路径、
无关账户、借款或固定资产信息。

### 7.3 AI 输出

模型输出必须解析为固定结构：

```text
category_key
rewrite_merchant
rewrite_product
status
confidence
```

`status` 至少支持：

- `classified`：可以分类；
- `unclassified`：无法分类；
- `need_review`：结果不确定；
- `error`：调用或解析失败。

写回前必须校验：

1. `classified` 时 `category_key` 存在，且分类处于启用状态并匹配收支类型；
2. 输出结构和字段类型合法；
3. `confidence` 在约定范围内；
4. `rewrite_merchant` 和 `rewrite_product` 不能是空字符串；空值表示不重写；
5. `unclassified`、`need_review` 和 `error` 不写入无效分类；
6. AI 建议不能绕过本次操作保护范围，也不能覆盖用户明确保护的草稿行。

### 7.4 AI 操作流

1. 用户在流水页进入批量选择模式并选中流水；
2. 点击“AI 分类”，先调用 API 并生成预览；
3. 按分类成功、无法分类、需要确认、调用失败、格式错误、分类标识无效分组展示；
4. 用户确认后，建议才进入当前草稿；
5. 用户保存流水时，仍由普通 Service/Repository 校验和写入；
6. 失败流水可以单独重试，也可以只重试指定错误类型；
7. AI 结果不自动生成永久规则；多个相同结果只允许提示用户创建普通规则，不能自动
   创建。

### 7.5 AI 审计

每个 AI 批次至少记录：

- 模型名称；
- 调用时间；
- 请求范围和数量；
- 返回状态；
- 原始结果；
- 用户最终采用结果；
- 失败原因或校验错误。

AI 审计是本地非财务元数据，不参与资产、消费、对账或规则计算。AI 子系统不得新增
专用财务事实表，也不得直接改写 SQLite；确认后的流水字段只能走现有保存路径。审计
元数据的具体本地存储载体在技术设计阶段确定，但必须能从批次结果入口查看。

## 8. P3：未来的代付关系模型（本阶段不做）

本节只记录方向，不纳入当前实现、当前验收或当前数据库修改。

### 8.1 交易与关联

1. 代付是入账侧的独立交易类型，但不直接作为普通收入统计；
2. 一笔代付可以关联一笔或多笔支出；
3. 一笔支出可以关联一笔或多笔代付；
4. 增加代付与支出的关联关系模型；
5. 关联记录至少包含代付流水 ID、支出流水 ID、关联金额、创建时间和创建方式；
6. 支持部分代付、一笔支出多人分摊和一笔代付覆盖多笔支出；
7. 关联金额不得超过代付和支出的剩余可关联金额。

### 8.2 状态与统计

代付状态至少包括：未关联、部分关联、已完全关联。

统计上必须同时保留：

- 原始支出金额；
- 他人代付金额；
- 个人实际承担金额；
- 未关联代付金额。

代付不计入普通收入；未关联代付单独展示，不自动抵扣消费。分类统计必须明确区分
原始消费、他人代付和个人实际承担金额。

### 8.3 对当前转换功能的影响

完整关系模型上线后，收入转代付和代付转回收入需要增加：

- 转回前检查现有关联；
- 已有关联时要求先解除或明确确认解除；
- 转换日志记录新增或解除的关联；
- 批量转换只允许处理符合关联状态的流水。

在此之前，当前阶段的转换只能是可追溯的交易类型转换，不能宣称已经完成代付抵扣或
个人承担额计算。

## 9. 不在本专项需求中的内容

- 新增顶层页面或把出账、入账、理财拆成三个 ItemView；
- 新增独立的商品或交易对手统计数据库；
- 正则、关键词、模糊匹配、自定义规则优先级；
- 规则修改后自动回写所有历史流水；
- AI 自动创建永久规则或直接写入财务事实；
- AI 代替普通规则冲突处理；
- 本阶段的代付支出关联、部分代付和个人承担额计算；
- 改变资产、对账、收入、支出、理财或固定资产的财务口径。

## 10. 验收主线

### 规则

- 三种规则都能精确匹配；
- 组合 > 商品 > 交易对手的固定优先级可解释；
- 同条件硬冲突不能保存；
- 不同作用域的覆盖不误报为冲突；
- 重写只执行一轮，潜在二次匹配链不能保存；
- 规则编号在规则表、流水详情和日志中一致；
- 修改或删除规则不会静默改历史。

### 流水与批量

- 出账、入账、理财 Tab 只展示适用类型和控件；
- 逐项、商品汇总、交易对手汇总都映射回相同原始流水 ID；
- 组选择、全选、全不选和逐笔选择范围准确；
- 普通应用规则、批量应用规则和 AI 分类范围符合模式定义；
- 所有批量修改都有数量、前后值、成功/失败/跳过和日志入口；
- 汇总界面创建规则前展示实际影响范围。

### AI

- API Key 不进入普通设置、SQLite、日志和请求正文中的非必要位置；
- 未配置 AI 时普通功能不受影响；
- 非法输出、无效分类和不确定结果不会写成有效分类；
- 预览确认后才进入草稿，保存仍走普通写入边界；
- 支持按错误类型重试，且不自动生成规则；
- 批次审计可以查看模型、时间、原始结果和最终采用结果。

### 未来代付

第 8 节只作为后续设计输入，不作为本阶段的验收项。

## 11. schema 10 数据库修改点（规划）

schema 10 只承载本轮已经确定的规则和分类定义数据结构变化。代付已经是现有的独立
交易类型，本轮只调整它在流水 UI 中归入“入账”Tab，不新增代付支出关联表。

### 11.1 必须新增或调整

1. **升级 schema 版本**
   - 数据库 `user_version`、应用返回的 `schema_version` 和 schema 校验目标从 9 升到 10；
   - 同步更新 schema 必需列、索引、备份清单和相关测试；
   - 由于备份列契约发生变化，备份格式版本同步升到下一版本，旧备份必须经过明确的兼容
     校验后才能恢复。
2. **分类定义增加正式字段**
   - `category_definitions` 增加 `description TEXT NOT NULL DEFAULT ''`；
   - 该字段是分类定义的正式持久化字段，不是 AI 配置字段，也不使用插件本地配置维护
     第二份副本；
   - 分类读取、编辑、revision 保存、默认分类初始化、备份和恢复都必须包含该字段；
   - 仅修改 `description` 不改写历史流水，也不改变规则结果。
3. **规则表泛化**
   - `auto_rules` 增加 `match_scope`，取值限定为 `product`、`merchant`、
     `merchant_product`；
   - 增加 `rewrite_merchant TEXT NOT NULL DEFAULT ''` 和
     `rewrite_product TEXT NOT NULL DEFAULT ''`；
   - 保留现有 `id` 作为规则编号，保留 `counterparty`、`product`、`category_key`、
     `transaction_type` 等字段；
   - `match_scope` 与条件必须满足：仅商品时只填商品，仅交易对手时只填交易对手，组合
     规则两者都非空；空条件、代付/加仓/提现规则和无效分类均不得写入；
   - 重写字段写入前统一规范化，空字符串和纯空格都表示“不修改”，不允许保存为清空
     交易对手或商品的规则。
4. **增加有效规则唯一约束**
   - 当前 `auto_rules` 中的规则行视为有效规则；数据库必须按
     `transaction_type + match_scope + 规范化后的匹配条件` 建立唯一约束或唯一索引；
   - 唯一约束必须覆盖仅商品、仅交易对手和交易对手 + 商品三种作用域，不能只依赖前端
     检查；
   - 如果原始文本字段无法直接表达规范化后的条件，需要增加内部规范化匹配键，或使用
     等价的数据库唯一表达式，但该实现字段不作为用户可编辑字段。
5. **保留现有事实表边界**
   - `transactions.type` 不新增类型；代付仍保留为代付类型，只在页面分组上归入入账；
   - 规则重写直接写入现有流水的交易对手和商品字段，不新增重复的重写结果列；
   - 规则编号使用 `auto_rules.id`，不额外增加一个含义重复的 `rule_no` 字段。

### 11.2 schema 10 迁移要求

1. 从 schema 9 升级时，已有分类的 `description` 统一回填为空字符串。
2. 已有规则根据非空条件回填 `match_scope`：仅商品、仅交易对手或组合规则；无法判定
   作用域的规则必须报告并阻止迁移完成。
3. 回填规范化匹配键并检查同收支类型、同作用域、同条件的重复规则；发现重复时不得
   静默选择，必须在建立唯一约束前让用户处理。
4. 迁移前创建保护备份，迁移、回填和索引创建在可回滚的事务边界内完成；任一步校验
   失败都不得覆盖原 schema 9 数据库。
5. 迁移完成后校验分类外键、规则分类有效性、唯一性、行数和备份恢复可用性。

### 11.3 明确不放入 schema 10 的内容

- 不新增 AI 专用财务表、AI 配置表或 AI 结果表；API 地址、模型、超时等留在设置中，
  API Key 使用 Obsidian SecretStorage；
- 不新增“人工锁定分类”字段；批量选择和本次跳过范围不形成持久化状态；
- 不新增代付与支出的关联关系表；多对多关联、部分代付和个人承担额属于第 8 节的
  未来方向；
- 不默认新增流水 `applied_rule_id`。当前规则编号可由规则解析结果得到；如果未来要求
  在规则删除或修改后仍保留写入时的历史命中关系，再单独设计审计关联模型。
