# 14 数据可信性模型

> 文档角色：开发与维护。这里连接产品理念、财务模型和技术架构；用户只需要在
> [隐私与备份说明](02-user-guide.md)中了解可执行的操作。

## 1. 核心命题

“SQLite 是唯一事实源”不仅是存储实现，也是产品信任承诺：用户看到的每个金额、
分类、资产和趋势，都应该来自同一套已经保存并经过校验的财务事实。

```text
支付平台账单
    ↓
导入与字段映射
    ↓
格式校验和统一语义
    ↓
SQLite 财务事实
    ↓
规则治理和用户确认
    ↓
统一财务计算
    ↓
资产、消费和趋势分析
```

## 2. 数据类型边界

| 类型 | 示例 | 是否是财务事实 | 维护要求 |
| --- | --- | --- | --- |
| 原始输入 | CSV、XLSX、XLS | 否 | 只作为导入来源，不直接参与分析 |
| 临时状态 | 导入预览、未保存草稿 | 否 | 可丢弃、可重建，不能冒充已保存数据 |
| 持久化事实 | SQLite 中的流水、账户、借款、资产、分类和规则 | 是 | 经过校验、事务和备份保护 |
| 派生结果 | 月度支出、储蓄率、趋势和商品汇总 | 否，来自事实计算 | 不维护第二份统计账本，可重新生成 |
| 用户输出 | 报告、导出和 Obsidian 展示 | 否 | 必须标明来自当前事实层 |

插件设置只保存界面设置和导入映射元数据，不保存第二套财务事实。

## 3. 五条可信性不变量

1. **单一写入边界**：财务事实只能通过 schema、Repository 和事务写入。
2. **单一计算口径**：月度、年度、商品、资产和对账指标复用同一领域定义。
3. **不静默改写**：规则建议、AI 建议和批量操作都不能未经确认修改历史。
4. **影响可见**：高影响修改先展示流水、月份、分类和金额的影响范围。
5. **可恢复**：备份能够恢复完整事实状态，失败恢复不能覆盖当前有效数据库。

## 4. 当前代码映射

| 可信性环节 | 当前入口 | 维护重点 |
| --- | --- | --- |
| 导入和统一语义 | `src/domain/csv.ts`、`src/ui/CsvImportDialog.tsx` | 显式映射收支，不凭平台文字猜测 |
| 草稿与质检 | `src/ui/csvImportCommit.ts`、编辑器 reducer | 未保存内容不能被当成事实 |
| 保存和事务 | `src/database/AssetTrackRepository.ts`、`DatabaseManager.ts` | revision、事务和原子失败 |
| 财务计算 | `src/domain/calculator.ts` | 公式只有一个事实实现和测试 |
| 资产与对账 | `src/database/AssetTrackRepository.ts`、分析模型 | 差额用于排查，不被图表掩盖 |
| 备份恢复 | `src/services/BackupService.ts` | 先验证、再快照、最后替换 |

新功能应先落到这些边界，再进入 UI；不得在 React 组件内复制金额、资产或对账计算。

## 5. 可追溯性要求

分析结果至少应能回答：

```text
这个数字是什么定义？
→ 来自哪些分类或商品？
→ 对应哪些流水？
→ 来自哪个月份和输入来源？
→ 哪些异常或人工判断影响了它？
```

当前实现已经提供逐笔流水、商品历史、规则冲突和回溯入口；导入批次、数据源覆盖和
重复风险属于后续增强，应在进入 schema 前先定义元数据边界和备份兼容策略。

## 6. 测试与发布约束

- 领域公式、导入映射、保存事务、revision、备份恢复和分析查询必须有对应测试。
- 缓存或汇总表可以删除后重建，不能作为绕过事实层的性能捷径。
- 任何 schema 变化都必须同步数据兼容、备份、恢复和发布说明。
- 发布前检查最终 bundle、三文件、版本、数据库边界和敏感文件排除；详见
  [构建与发行](07-release.md)。
